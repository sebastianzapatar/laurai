La aplicación

Una API REST sencilla: chefs y sus platos

🎯 Qué hay que desplegar

Un contenedor Docker con Spring Boot 4 (Java 25) escuchando en el puerto 6969, conectado a una base de datos PostgreSQL.

MétodoRutaQué hace
GET/api/chefsLista chefs
POST/api/chefsCrea un chef
GET/api/dishesLista platos
GET/api/dishes/chef/{id}Platos de un chef
POST/api/dishesCrea un plato
GET/actuator/healthHealth check del ALB

✂️ Se quitó Keycloak

Antes la API validaba tokens JWT emitidos por Keycloak, lo que obligaba a desplegar otro servidor en AWS y a pasar KEYCLOAK_ISSUER_URI por todo el pipeline.

Para simplificar se eliminaron: Spring Security / OAuth2, el contenedor de Keycloak en compose.yml, el parámetro SSM, la variable de Terraform y el secret de GitHub.

⚠️ Consecuencia

Ahora cualquiera que conozca la URL del ALB puede crear chefs y platos. Está bien para una clase o demo; para producción habría que volver a poner autenticación (Cognito, API Gateway o Keycloak).

  1. El usuario llama al ALB, el único componente con IP pública.
  2. El ALB reenvía al contenedor en ECS Fargate, que vive en una subred privada.
  3. El contenedor consulta RDS, también privado: solo el contenedor puede hablarle.
  4. Para descargar la imagen y leer secretos, ECS sale a Internet por el NAT Gateway.
  5. GitHub Actions crea todo con Terraform y publica cada versión nueva.
🧱 Infraestructura como código terraform/

Terraform: módulos y estado

Describes lo que quieres; Terraform calcula qué crear, cambiar o borrar

terraform/
├── main.tf            ← orquesta los módulos + backend S3
├── variables.tf       ← región, nombre, DB, CPU/RAM…
├── outputs.tf         ← URL del ALB, URL de ECR…
├── terraform.tfvars.example
└── modules/
    ├── network/   VPC, subredes, IGW, NAT, rutas
    ├── ecr/       repositorio de imágenes
    ├── rds/       PostgreSQL + su security group
    ├── ssm/       parámetros SecureString
    └── ecs/       cluster, task, service, ALB, IAM, logs
🔗

Orden de creación

Terraform deduce el orden a partir de las referencias: network → SG de ECS → rds → ssm (necesita el endpoint de RDS) → task definition y servicio de ECS.

terraform {
  required_version = ">= 1.5.0"

  # El estado vive en S3; DynamoDB evita
  # que dos personas hagan apply a la vez
  backend "s3" {
    bucket         = "laura-tf-state-xyz89b"
    key            = "lauracanceleatiempo/terraform.tfstate"
    region         = "us-east-2"
    dynamodb_table = "laura-tf-locks-xyz89b"
    encrypt        = true
  }
}

module "ssm" {
  source      = "./modules/ssm"
  db_url      = "jdbc:postgresql://${module.rds.db_endpoint}/${var.db_name}"
  db_username = var.db_username
  db_password = var.db_password
  # ...
}

🌐 Red modules/network

VPC, subredes, IGW y NAT

Amazon Virtual Private Cloud

🎯 Propósito

Crear una red aislada dentro de AWS y decidir qué partes son visibles desde Internet (públicas) y cuáles no (privadas).

🏗️ Qué crea este módulo

  • VPC 10.0.0.0/16 con DNS habilitado.
  • 2 subredes públicas (10.0.0.0/24, 10.0.1.0/24) para el ALB y el NAT.
  • 2 subredes privadas (10.0.10.0/24, 10.0.11.0/24) para ECS y RDS.
  • Internet Gateway: puerta de entrada/salida de las públicas.
  • NAT Gateway + IP elástica: las privadas pueden salir a Internet pero nadie puede entrar.
  • Dos tablas de rutas: pública → IGW, privada → NAT.
resource "aws_subnet" "private" {
  count             = 2
  vpc_id            = aws_vpc.main.id
  cidr_block        = "10.0.${count.index + 10}.0/24"
  availability_zone = data.aws_availability_zones.available.names[count.index]
}

resource "aws_nat_gateway" "main" {
  allocation_id = aws_eip.nat.id
  subnet_id     = aws_subnet.public[0].id
}

resource "aws_route_table" "private" {
  vpc_id = aws_vpc.main.id
  route {
    cidr_block     = "0.0.0.0/0"
    nat_gateway_id = aws_nat_gateway.main.id
  }
}
🏢

Analogía

La VPC es un edificio de oficinas. La recepción (subred pública) da a la calle; las oficinas (subredes privadas) no tienen puerta a la calle. El NAT es el mensajero: puede salir a hacer recados por ellas, pero nadie de afuera entra por él.

Security Groups

Un firewall con estado alrededor de cada componente

🎯 Propósito

Permitir solo el tráfico estrictamente necesario, encadenando los grupos: cada capa solo acepta conexiones de la capa anterior.

Security GroupEntrada permitidaDesde
laura-alb-sg80, 443 / TCP0.0.0.0/0 todo Internet
laura-ecs-sg6969 / TCPlaura-alb-sg
laura-rds-sg5432 / TCPlaura-ecs-sg
🔗

Cadena de confianza

Internet → ALB → ECS → RDS. Como las reglas apuntan a otro security group y no a IPs, siguen funcionando aunque las tareas de Fargate cambien de IP en cada despliegue.

resource "aws_security_group" "rds" {
  name   = "${var.project_name}-rds-sg"
  vpc_id = var.vpc_id

  ingress {
    from_port       = 5432
    to_port         = 5432
    protocol        = "tcp"
    # solo las tareas de ECS
    security_groups = [var.ecs_sg_id]
  }
}
📦 Contenedores modules/ecr

ECR — Elastic Container Registry

El "Docker Hub privado" de tu cuenta de AWS

🎯 Propósito

Guardar las imágenes Docker de la API para que ECS pueda descargarlas sin depender de un registro externo.

🏗️ En este proyecto

  • Repositorio laura-api.
  • Cada push a main sube dos tags: el SHA del commit (inmutable en la práctica) y latest.
  • Escaneo de vulnerabilidades automático en cada push.
  • Lifecycle policy: conserva solo las últimas 10 imágenes para no pagar almacenamiento de más.
  • force_delete = true: terraform destroy puede borrarlo aunque tenga imágenes.
resource "aws_ecr_repository" "app" {
  name                 = "${var.project_name}-api"
  image_tag_mutability = "MUTABLE"
  force_delete         = true

  image_scanning_configuration {
    scan_on_push = true
  }
}

resource "aws_ecr_lifecycle_policy" "cleanup" {
  repository = aws_ecr_repository.app.name
  policy = jsonencode({
    rules = [{
      rulePriority = 1
      selection = {
        tagStatus   = "any"
        countType   = "imageCountMoreThan"
        countNumber = 10
      }
      action = { type = "expire" }
    }]
  })
}
🐳 Cómputo modules/ecs

ECS con Fargate

Elastic Container Service · contenedores sin administrar servidores

🎯 Propósito

Ejecutar el contenedor de la API, mantener siempre N copias vivas y reemplazarlas sin cortar el servicio cuando sale una versión nueva.

  1. Cluster laura-cluster: agrupación lógica, con Container Insights activado.
  2. Task definition laura-api-task: "la receta" (imagen, 0.5 vCPU, 1 GB, puerto 6969, secrets, logs, health check).
  3. Service laura-api-service: mantiene desired_count tareas corriendo y las registra en el ALB.
🔁

Despliegues sin caída

minimum_healthy = 100% y maximum = 200%: primero arranca la tarea nueva, luego apaga la vieja. Si la nueva no pasa el health check, el circuit breaker hace rollback automático.

resource "aws_ecs_service" "app" {
  name            = "${var.project_name}-api-service"
  cluster         = aws_ecs_cluster.main.id
  task_definition = aws_ecs_task_definition.app.arn
  desired_count   = var.desired_count
  launch_type     = "FARGATE"

  network_configuration {
    subnets          = var.private_subnet_ids
    security_groups  = [aws_security_group.ecs.id]
    assign_public_ip = false
  }

  deployment_circuit_breaker {
    enable   = true
    rollback = true
  }

  lifecycle {
    # el CI/CD cambia la revisión; Terraform no la revierte
    ignore_changes = [task_definition, desired_count]
  }
}
🍽️

Analogía

La task definition es la receta, la tarea es el plato servido y el service es el jefe de cocina que se asegura de que siempre haya el número de platos pedido; si uno se cae, prepara otro.

⚖️ Red modules/ecs

ALB — Application Load Balancer

La única puerta pública de la aplicación

🎯 Propósito

Recibir el tráfico HTTP de Internet y repartirlo solo entre las tareas de ECS que estén sanas.

🏗️ Tres piezas

  • Load balancer laura-alb en las dos subredes públicas. Su DNS es la URL de la API (output alb_dns_name).
  • Listener en el puerto 80 que reenvía todo al target group.
  • Target group laura-tg de tipo ip (obligatorio para Fargate) que llama a /actuator/health cada 30 s.

Una tarea entra en rotación tras 2 health checks OK y sale tras 5 fallidos.

resource "aws_lb_target_group" "app" {
  name        = "${var.project_name}-tg"
  port        = var.container_port   # 6969
  protocol    = "HTTP"
  vpc_id      = var.vpc_id
  target_type = "ip"                 # Fargate

  health_check {
    path                = "/actuator/health"
    healthy_threshold   = 2
    unhealthy_threshold = 5
    interval            = 30
    matcher             = "200"
  }
}

resource "aws_lb_listener" "http" {
  load_balancer_arn = aws_lb.main.arn
  port              = 80
  protocol          = "HTTP"
  default_action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.app.arn
  }
}

IAM — los dos roles de ECS

Identity and Access Management · quién puede hacer qué

🚚 Execution role · laura-ecs-execution-role

Lo usa el agente de ECS antes de arrancar tu contenedor.

  • Descargar la imagen de ECR.
  • Escribir logs en CloudWatch.
  • Leer los 3 parámetros de SSM (política laura-ecs-ssm-read).

⚙️ Task role · laura-ecs-task-role

Lo usa tu aplicación mientras corre, si llama a la API de AWS.

  • Hoy está vacío: la API solo habla con PostgreSQL.
  • Si mañana sube archivos a S3 o manda mensajes a SQS, el permiso se agrega aquí.
resource "aws_iam_role_policy" "ecs_ssm_read" {
  name = "${var.project_name}-ecs-ssm-read"
  role = aws_iam_role.ecs_execution.id
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect   = "Allow"
      Action   = ["ssm:GetParameters", "ssm:GetParameter", "kms:Decrypt"]
      Resource = var.ssm_parameter_arns   # solo estos 3 parámetros
    }]
  })
}

🪣 Datos backend "s3"

S3 + DynamoDB: el estado de Terraform

La "memoria" de Terraform, compartida entre tu máquina y GitHub Actions

😟 Problema

Terraform guarda en terraform.tfstate qué recursos creó. Si ese archivo vive en el runner de GitHub Actions, se pierde al terminar el job: el siguiente push intentaría crear todo otra vez y chocaría con lo que ya existe.

💡 Solución

El estado se guarda en el bucket S3 laura-tf-state-xyz89b (con versionado) y la tabla DynamoDB laura-tf-locks-xyz89b pone un candado para que dos apply no corran a la vez.

El workflow crea ambos si no existen, antes de terraform init.

⚠️ Los nombres de bucket son globales

Si despliegas en otra cuenta (por ejemplo, desde un fork), el bucket laura-tf-state-xyz89b ya es de otra persona y la creación falla. Cómo renombrarlo en los 3 archivos que lo usan: paso B3.

🚀 CI/CD .github/workflows/aws-ecs.yml

El pipeline: 2 jobs

Se dispara con cada push a main, salvo si solo cambian docs/ o archivos .md

🏗️ Job 1 · Terraform

  1. Configura credenciales de AWS desde los secrets.
  2. Crea (si no existen) el bucket S3 y la tabla DynamoDB del estado.
  3. terraform init → validate.
  4. terraform plan -var="db_password=…".
  5. terraform apply plan.out.
  6. Publica el DNS del ALB como output del job.

🐳 Job 2 · Build & Deploy

  1. Login en ECR.
  2. docker build (Maven compila dentro del Dockerfile).
  3. docker push con tags <sha> y latest.
  4. Descarga la última revisión de laura-api-task.
  5. Le cambia la imagen por la del commit.
  6. Despliega en ECS y espera a que el servicio quede estable.
  7. Escribe la URL de la API en el resumen del run.
🧠

¿Por qué Terraform no construye la imagen?

Terraform describe infraestructura (lo que cambia poco); el pipeline publica versiones de la app (lo que cambia en cada commit). Por eso el servicio tiene ignore_changes = [task_definition]: Terraform no deshace lo que despliega el CI.

☁️ Paso A1 Consola de AWS

Cuenta, región y alerta de costos

Antes de crear nada, asegúrate de estar en el lugar correcto

1️⃣ Entra a la consola

Abre console.aws.amazon.com e inicia sesión. Si no tienes cuenta: Create an AWS account. Pide correo, tarjeta y verificación por teléfono.

2️⃣ Elige la región Ohio

Arriba a la derecha está el selector de región. Elige:

US East (Ohio) us-east-2

Todo el proyecto vive ahí. Si estás en otra región, no verás el cluster, la base de datos ni el ALB y parecerá que no se creó nada.

3️⃣ Crea una alerta de presupuesto recomendado

Billing and Cost Management›Budgets›Create budget
  1. Elige Use a template → Monthly cost budget.
  2. Monto: por ejemplo 20 USD.
  3. Escribe tu correo en Email recipients.
  4. Create budget.
💸

¿Por qué?

Esta infraestructura cuesta unos 3 USD por día encendida. Si olvidas destruirla, el correo te avisa antes de que la factura crezca.

☁️ Paso A2 Consola de AWS → IAM

Crear el usuario IAM del pipeline

La identidad con la que GitHub Actions entra a tu cuenta de AWS

🎯 Para qué

GitHub no puede usar tu usuario personal ni tu contraseña. Necesita un usuario propio, solo para máquinas, con llaves que puedas revocar cuando quieras.

Buscar "IAM"›Users›Create user
  1. User name: github-actions-laura.
  2. No marques "Provide user access to the AWS Management Console": este usuario nunca entra a la consola.
  3. Next. Llegas a la pantalla de permisos, que es el paso A3.

☁️ Paso A3 Set permissions

Darle permisos al usuario

Elige una de las dos opciones

Opción 1 · Rápida (cuenta de pruebas / clase)

  2. Busca AdministratorAccess y márcala.

🔐 Cómo generar DB_PASSWORD

# 32 caracteres hexadecimales: siempre válida para RDS

RDS exige 8–128 caracteres y no acepta /, @, " ni espacios. Guárdala también en tu gestor de contraseñas.

⚠️ Escógela una vez y no la cambies

Terraform crea RDS con esa contraseña y luego la ignora (ignore_changes = [password]). Si cambias el secret después, SSM recibe la nueva pero RDS sigue con la vieja y la app no podrá conectarse. Para cambiarla: cámbiala también en RDS (Modify) o destruye y vuelve a crear todo.

Revisión: qué se corrigió

Cambios hechos al revisar Terraform y el pipeline

Corregido

  • Se quitó el step "Limpiar recursos residuales": en cada push borraba RDS, ALB, ECR y roles IAM que Terraform ya gestionaba desde S3. Perdías la base de datos en cada deploy.
  • La task definition ya no ignora container_definitions: si cambian los secrets en Terraform, se registra una revisión nueva que el CI usa en el siguiente deploy.
  • El health check del contenedor usaba curl, que la imagen eclipse-temurin:25-jre no trae; ahora el Dockerfile lo instala.
  • Keycloak fuera de Terraform, SSM, ECS, workflows, compose.yml y Spring.
  • compose.yml mapeaba 6969:8080 pero la app escucha en 6969.
  • @Valid no validaba nada (faltaba Hibernate Validator) y @NotBlank en un BigDecimal habría lanzado 500.

Pendiente (recomendado)

  • Solo hay listener HTTP en el 80; el SG abre el 443 sin listener. Para HTTPS: certificado de ACM + listener 443.
  • engine_version = "16.6" fijo: cuando AWS retire esa versión menor, el apply fallará. Usar "16".
  • RDS sin backups ni Multi-AZ: aceptable para clase, no para producción.
  • Llaves de acceso estáticas en GitHub: migrar a OIDC.
  • El job de deploy instala JDK 21 aunque el build ocurre dentro de Docker con Java 25: el step sobra.
  • JaCoCo 0.8.12 no soporta Java 25: mvn verify falla; subir a 0.8.14.

Resumen

Lo que hay que llevarse

🌐 Red en capas

Solo el ALB es público. ECS y RDS viven en subredes privadas, y los security groups encadenan ALB → ECS → RDS.

🐳 Contenedor administrado

ECR guarda la imagen, ECS Fargate la ejecuta y la reemplaza sin caída; el circuit breaker revierte si algo sale mal.

🔐 Secretos fuera del código

La contraseña viaja de GitHub Secrets → Terraform → SSM → variable de entorno del contenedor.

🧱 Estado compartido

S3 + DynamoDB permiten que el pipeline y tu PC trabajen sobre la misma infraestructura sin pisarse.

🚀 Infra vs. versiones

Terraform crea la infraestructura; el pipeline publica versiones de la app. Cada uno ignora lo que gestiona el otro.

💸 Apagar al terminar

NAT, ALB y Fargate cobran por hora. Despliega, prueba y corre el workflow de destroy.

git push terraform apply docker push ecs deploy curl /actuator/health terraform destroy
